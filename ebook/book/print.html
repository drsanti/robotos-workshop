1. Motivation

Robot middleware is a graph of programs talking over named topics. Your laptop will run:

  1. CLI tools (robotos) — list topics, echo messages, record bags
  2. Python scripts — your labs publish and subscribe
  3. Warehouse sim (WH labs) — a desktop app that is the robot on the graph
  4. Optionally a serial-bridge (HW labs) — connects a real ESP32-S3 board

If PATH, the Python wheel, or the sim connection is wrong, every later lab looks “broken.” This chapter removes that fog.

Chapter 1 — Graph, nodes, and topics

Learning outcomes

You can explain, in your own words:

  • What a node is vs a topic
  • Why message schemas matter
  • How discovery (topic list) relates to “is anyone there?”
  • Why the warehouse teaching contract uses fixed names under /robot/01/

Prerequisites

  • Chapter 0 complete (robotos version works)
  • Optional: warehouse sim running for the hands-on section

1. Motivation / story

Imagine three classmates each writing a program:

  • One drives the robot (publishes velocity commands)
  • One logs position (subscribes to odometry)
  • One draws a map (subscribes to laser scans)

They should not hard-code each other’s IP ports or call each other’s functions. Instead they agree on names and message shapes. That agreement is the graph.

robotos (like ROS-style systems) implements that idea with:

  • Nodes — running programs
  • Topics — named buses for streaming data
  • Schemas — protobuf types so bytes are meaningful

2. Theory (detailed)

2.1 The graph is not one process

A common beginner mistake: “the simulator is the whole system.”
In WH labs the desktop sim is one node (robotos_sim). Your Python script is another. The CLI (robotos topic echo) can be a third.

They meet on a shared transport (Zenoh under the hood). You rarely configure Zenoh by hand in this workshop: multicast peer mode on the lab LAN, or ROBOTOS_CONNECT when a bridge listens on TCP.

2.2 Topics are contracts

Example contract (warehouse P0):

TopicWho publishesWho typically subscribesSchema
/robot/01/cmd_velYour controllerSim (or robot)robotos.geometry.v1.Twist
/robot/01/odomSim / robotYour controller / loggerrobotos.nav.v1.Odometry
/robot/01/scanSim / robotAvoidance / mappingrobotos.sensor.v1.LaserScan

Direction is convention: commands in toward the robot, sensors out toward learners. The middleware will not stop you from publishing on odom — but you would break the teaching contract and confuse every other node.

2.3 Schemas (protobuf)

A topic carries bytes. Without a schema, subscribers cannot know whether those bytes are a Twist or a JPEG. In Python starters you see:

from robotos.messages.robotos.geometry.v1.geometry_pb2 import Twist
pub = node.create_publisher("/robot/01/cmd_vel", Twist)

That second argument ties the topic to a type. CLI topic list shows the schema column so you can verify the contract at runtime.

2.4 Discovery vs data

  • Discovery: “Who announced what?” → robotos topic list, robotos node list
  • Data: “What values are flowing?” → robotos topic echo …, your subscriber callbacks

Empty topic list does not mean robotos is broken. It usually means no node has joined (sim not connected, wrong env, bridge down).

2.5 Native vs Mock (warehouse UI)

ModeMeaning for graded labs
Native + ExternalReal graph; your scripts may drive the robot
ManualOperator owns motion; your cmd_vel is ignored for motion
MockUI fakes a learner — not for graded graph work

Workshop rule: graded WH work uses the real graph (Native), not Mock.

Chapter 2 — Twist commands & control ownership

Learning outcomes

  • Map Twist.linear.x / Twist.angular.z to warehouse motion
  • Explain why External + Native is required for graded drive labs
  • Explain the 500 ms command timeout and why labs publish in a loop
  • Run WH-01 from the workshop root on Windows or Unix

Prerequisites

  • Chapter 0–1; sim connected
  • Lab WH-00 done

1. Motivation

Your script is not “calling the simulator API.” It is publishing velocity setpoints on a topic. If nobody is listening under External ownership, or if you publish too slowly, the robot will not do what you expect.

2. Theory

2.1 Twist fields that matter (P0 warehouse)

FieldUnitEffect
linear.xm/sForward (+) / reverse (−)
angular.zrad/sYaw left/right

Other components are ignored in the P0 warehouse model. The sim clamps speeds (|v| ≤ 0.5, |ω| ≤ 1.5 by contract) — huge numbers do not make a race car.

2.2 Control ownership

UI modeWho moves the robot?
ManualKeyboard / on-screen teleop
ExternalMessages on /robot/01/cmd_vel
MockFake learner inside the UI — not your Python node on the real graph

Graded path: External + Native + Connect.
“Bridge” in some UI tables means an instructor web demo path — not the HW serial-bridge tool.

2.3 Command timeout (500 ms)

If External is selected but no fresh Twist arrives within ~500 ms, the sim stops applying motion. Consequences:

  • A single publish is not enough — use a rate loop (≥ ~2 Hz; WH-01 uses 20 Hz).
  • Stopping your script (or network blip) fails safe toward “stop.”
  • Still publish an explicit zero Twist() on exit — good habit even with timeout.

Chapter 5 — Feedback vs open loop

Learning outcomes

  • Contrast open-loop timed commands with closed-loop sensor-based commands
  • Describe bang-bang control and its chatter failure mode
  • Explain why WH-03 must keep publishing against the 500 ms timeout

Prerequisites

  • Chapters 2–3; labs WH-01 / WH-02

1. Motivation

WH-01 proved you can move. WH-02 proved you can see. Feedback ties them: command = f(sensors) so the robot reacts to the world instead of hoping a timer is enough.

2. Theory

2.1 Open loop

cmd = f(time) — e.g. “drive 2 s, turn 1 s, repeat.” Easy to write; blind to walls and slip. WH-04 uses this on purpose so you feel the failure after seeing feedback win in WH-03.

2.2 Closed loop

cmd = f(sensors) — WH-03 reads front range and chooses creep vs turn.

2.3 Bang-bang

Discrete thresholds (“too close / OK”), not continuous PID yet. Good first controller; classic failure: chatter if the measurement oscillates around the threshold.

2.4 Timing math (still approximate)

Distance ≈ (v \cdot \Delta t), angle ≈ (\omega \cdot \Delta t). Clamps, discrete steps, and collisions break perfection even when odom is “perfect integration.”

2. Theory

StuckAll ranges tight → RECOVER, not infinite AVOID chatter
